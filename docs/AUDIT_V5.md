# Taskly V5 — Sécurité et préparation de la validation

Version cumulative de préproduction, issue directement du ZIP V4. Aucun déploiement, aucune modification de GitHub, Vercel, TiDB, Redis, Brevo ou DNS. Les corrections V1–V4 sont conservées, avec leurs limites. Taskly Mail doit rester désactivé.

## Corrections V5

- `server/middleware/securityMiddleware.js` : le contrôle CSRF, monté sur `/api`, s'applique à toutes les méthodes mutantes sans filtrer à nouveau le chemin brut. L'ancien test `startsWith('/api/')` sensible à la casse pouvait ignorer le contrôle alors qu'Express fait normalement correspondre les routes sans distinction de casse. Les méthodes GET/HEAD/OPTIONS restent exemptées, les jetons hexadécimaux et la comparaison constante sont conservés. Réponse CSRF `private, no-store`. Les routes de casse différente partagent également le même quota général Redis. Ce changement renomme les clés des chemins qui contenaient des majuscules lors du calcul antérieur ; les anciennes clés expirent normalement.
- `server/middleware/passwordResetLimiter.js` : réponse Redis incohérente (compteur non entier/inférieur à 1, TTL négatif ou non fini) refusée avec 503. Accès facultatif à l'adresse de socket. Quotas existants préservés.
- `server/app.js` : politique de cache privée appliquée avant le parsing JSON et le stockage de session pour couvrir également leurs erreurs. La sélection du contexte de session tient compte de la casse de la route et du slash final ; les cookies et les vérifications de rôle restent séparés. Le cron exige un en-tête Authorization de type Bearer explicite. Le gestionnaire d'erreur délègue si les en-têtes ont déjà été envoyés. `index.js` : réponse de démarrage 503 non cachable, journalisation limitée au code/type de l'erreur.
- `server/services/emailService.js`, `adminMailService.js`, `tasklyMail.js` : imposer STARTTLS en production quand la connexion n'utilise pas déjà TLS implicite. Délais de connexion, salutation et socket configurés sur les trois transports. Cela peut refuser un serveur SMTP mal configuré ; ne pas contourner TLS pour rétablir l'envoi. Aucun SMTP réel contacté. Le mécanisme de distribution de la file, les réessais et les doublons possibles lors d'une interruption restent à examiner.
- `.github/workflows/taskly-ci.yml` : contrôle sur pull request ou lancement manuel, Node 22, `npm ci`, syntaxe, tests et audit de dépendances. Permissions du workflow en lecture et pas de secrets de production injectés. Le nouveau workflow n'a pas été exécuté ici. L'audit npm en ligne n'a pas été réalisé.
- `.github/workflows/taskly-session-expiry.yml` : le job qui utilise l'URL de production existante ne peut être lancé que sur la branche par défaut. Ne pas déclencher le workflow de production pendant les tests.
- `scripts/load-test.k6.js` : scénario initial de lecture publique uniquement, cinq utilisateurs virtuels par défaut, maximum 25, consentement explicite, seuils et redirections interdites. Localhost ou hôte de préproduction Vercel explicitement confirmé ; l'URL de production connue est interdite. Le contrôle ne peut pas déterminer si un autre alias Vercel pointe en réalité vers la production : vérifier l'environnement, la base et le consentement de l'hébergeur. Aucun trafic de charge généré. Ce scénario n'évalue pas encore les parcours connectés ni la capacité d'un million de comptes.

## Résultats effectivement obtenus

- Tentative `npm ci --offline --no-audit --no-fund` bloquée (`ENOTCACHED`, paquet wrappy absent du cache). Le dossier partiellement installé a été retiré. Pas de dossier node_modules dans le ZIP.
- `npm run check` : 187 fichiers JavaScript, 0 erreur de syntaxe ; le script k6 au format module n'est pas inclus dans ce comptage.
- `node --test tests/audit-v5.test.js` : 8/8 tests ciblés passent. Tests de logique et simulation Redis/SMTP, initialisation du scénario k6 sans générer de requête.
- `npm test` : 276 réussites / 287 résultats ; 11 échecs `MODULE_NOT_FOUND` (Express, bcrypt, Nodemailer, multer), mêmes blocages qu'en V4. Les assertions HTTP ajoutées à `tests/http.test.js` pour les routes API en majuscules et le cache des erreurs de parsing n'ont donc pas été exécutées jusqu'au bout.
- Les sorties de syntaxe et de la suite sont conservées dans `docs/TESTS_AUDIT_V5.txt`. Aucun test de navigateur réel, base réelle, SMTP, Redis réel ni charge. Les tests réussis ne valent pas validation de production.

## Plan de déploiement contrôlé (ordre recommandé)

1. Sauvegarder le code actuel et relever le commit de production GitHub/Vercel. Créer une branche séparée, par exemple `audit/taskly-v5`, à partir de la version actuelle. Vérifier les différences avec le ZIP avant publication, ne pas écraser des modifications intervenues depuis le ZIP initial. Ne pas publier de fichier `.env`, de clé, de dump ou de dossier privé. Les fichiers de test et rapports sont conservés pour l'audit.
2. Sur une machine Node 22 avec accès au registre npm : `npm ci`, `npm run check`, `npm test`, `npm audit --omit=dev --audit-level=high`. Vérifier aussi les résultats du workflow CI. Corriger les échecs réels et les vulnérabilités avant toute ouverture publique. Ne pas lancer `npm audit fix --force` aveuglément.
3. Une base TiDB de test séparée, un Redis de test séparé, et une configuration SMTP de test autorisée. Sauvegarde vérifiée avant migration, puis appliquer uniquement les migrations nécessaires à l'état du schéma de test. Voir V1–V4 pour l'ordre, notamment la migration `migration_confidentialite_artisan.sql` ; contrôler les quatre colonnes. Ne pas réimporter `taskly_db.sql` sur une base existante. Ne pas lancer de migration sur production avant validation, et ne pas supposer qu'un DDL TiDB peut être annulé transactionnellement. Garder les deux flags Taskly Mail à false. Les migrations du pilote Mail ne sont nécessaires que pour un test dédié, selon AUDIT_V4.
4. Dans Vercel, lier le projet et générer une Preview, sans fusionner dans la branche de production. Les variables Preview ne doivent pas désigner les services de production. Vérifier `DB_SSL`, l'URL Redis TLS, `SESSION_SECRET` dédié, `ADMIN_ENTRY_PATH`, `PUBLIC_SITE_URL` de test, `TRUST_PROXY` adapté et les paramètres SMTP. Vérifier que les secrets sont séparés, et que le worker/cron ne touche pas les données reales. Garder `TASKLY_MAIL_PILOT_ENABLED=false`, `TASKLY_MAIL_GATEWAY_ENABLED=false`. Ne pas partager ces valeurs dans le chat.
5. Parcours navigateur : accueil, inscription, verification, mot de passe oublié, choix Client/Artisan 1/Artisan 2, refus d'accès croisé, administration séparée. Tester demandes, annulation, acceptation, chat, avis, photos, documents, profil, confidentialité et déconnexion. Tester fenêtres Client/Artisan/Admin sur ordinateur et mobile, absence de flou, conservation des tailles, du logo et du menu, clavier, fermeture et focus. Vérifier erreurs réseau et HTTP, rétablissement après panne, session expirée/révoquée et non-cachage. Les demandes en double et la concurrence nécessitent des tests réalistes.
6. Mesurer la latence Preview : régions Vercel, TiDB et Redis avec mesures répétées, temps de démarrage à froid et chaud, p50/p95/p99, erreurs 429/503, CPU/mémoire/quotas. Activer `TASKLY_PERF_TIMING=true` uniquement pendant le diagnostic de préproduction. Comparer les mêmes parcours avant/après, et désactiver le flag après mesure. Ne pas changer les régions à l'aveugle.
7. Charge initiale après accord explicite, uniquement sur environnement isolé : `TASKLY_LOAD_TEST=YES k6 run scripts/load-test.k6.js` en local (adapter la syntaxe de la variable au terminal). Pour une Preview vérifiée, fournir `TARGET_URL` et `PREVIEW_HOST`, initialement avec 5 VU. Ne pas augmenter avant contrôle de capacité et de coûts. Un véritable plan avec données synthétiques doit ensuite mesurer les parcours de travail représentatifs et la concurrence. Un million de comptes enregistrés ne signifie pas un million de connexions simultanées.
8. Taskly Mail : choisir et implémenter la passerelle réelle, domaine/DNS, cycle de vie, suspension et suppression, authentification professionnelle, gestion de la boîte, pièces jointes et antispam ; voir AUDIT_V4. Tester séparément avant activation. Pas d'application mobile dans cette mission. Ne pas activer le pilote sur la version publique avec cette seule archive.
9. Si et seulement si les contrôles de préproduction sont concluants : validation explicite, sauvegarde récente, plan de rollback (commit/déploiement précédent et restauration de données distincte des migrations de schéma), puis déploiement progressif. Surveiller erreurs et latence et conserver une possibilité de retour arrière. La V5 ne donne pas une autorisation de fusion ou de publication.

## Points encore ouverts

- Suite intégrale avec dépendances réelles, audit npm, contrôle visuel et tests d'intégration TiDB, Redis et Brevo, sécurité de l'hébergement et protection des clés, limites de coûts.
- Couverture de sécurité et fonctionnelle des quatre espaces non exhaustive ; une politique CSP complète, la validation approfondie des fichiers et le cycle de vie des données restent à auditer.
- Aucune mesure post-correction en production, aucune preuve de capacité à 1 million de comptes ni de stabilité sous forte charge. L'optimisation SQL et du cache doit être validée par mesures et plans d'exécution réels.
- Taskly Mail V4 n'est pas une véritable messagerie opérationnelle. Les limites et choix de la V4 restent ouverts.
