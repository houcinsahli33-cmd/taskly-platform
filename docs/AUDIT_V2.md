# Taskly — V2, préproduction uniquement

Suite de la V1, sans intervention sur le dépôt GitHub, les données ou les services de production. Conserver `AUDIT_ET_DEPLOIEMENT_2026-11-19.md` : ses restrictions et instructions restent applicables. Cette V2 remplace la V1 comme candidat de préproduction, pas comme version validée.

## Changements V2

- `server/middleware/authMiddleware.js` : les contrôles de rôle successifs réutilisent le résultat SQL vérifié pour **la même requête uniquement**, via WeakMap. Les demandes Artisan utilisant les deux contrôles passent de trois lectures de vérification (utilisateur, artisan, artisan) à deux. Les routes admin protégées par les deux middlewares passent de deux lectures à une. Chaque nouvelle requête continue à interroger la base. Vérification admin autonome renforcée (compte actif, email vérifié, version de session). Pas de cache des permissions entre requêtes.
- `server/middleware/securityMiddleware.js` : remplacement du compteur général local par un compteur Redis atomique en production ou si REDIS_URL est configuré. Conservation des seuils et fenêtres existants, mais quota partagé par modèle de route (les identifiants variables ne permettent plus de contourner ce quota). Clé HMAC, TTL, Retry-After, refus 503 si Redis indisponible. En développement sans Redis, mémoire plafonnée à 20 000 entrées. Les limiteurs spécifiques réinitialisation/coordonnées ne sont pas modifiés. Le réglage proxy/IP et l'effet des quotas sur utilisateurs partageant une IP doivent être testés avant fusion ; une limitation complémentaire par compte/cible reste à concevoir. Ce changement ajoute un aller-retour Redis aux routes ainsi protégées : mesurer latence et quotas. Pas de test sur Redis réel ici.
- `client/public/js/api.js` : partage des seules lectures simultanées ordinaires de `/api/account` dans un même document. Aucun stockage durable ; libération après succès ou échec ; mutation invalide la référence. Pas de cache de session, aucune restriction de sécurité supprimée. Le navigateur doit confirmer qu'une seule lecture est envoyée pour les composants de profil concurrents.
- `server/middleware/publicFiles.js`, `server/app.js` : ressources CSS/JS/images/polices fixes publiques servies avant le middleware session dans l'application locale ; HTML/JSON et API exclus de ce nouveau raccourci. Le point d'entrée Vercel (`index.js`) servait déjà les fichiers publics avant initialisation ; aucun gain Vercel supplémentaire revendiqué pour ce point.
- `server/models/chatModel.js`, `server/models/demandeModel.js` : masquage SQL du numéro d'artisan dans le chat et la liste de demandes client, sauf préférence explicite et profil approuvé, actif, e-mail vérifié. La valeur est NULL sinon. Le contrôle d'accès aux demandes reste inchangé ; l'administration garde les accès propres à ses missions. **Migration confidentialité de V1 à appliquer et vérifier sur la base de test avant d'utiliser ce code**, y compris si elle a déjà été appliquée sur la base réelle. Décision : le téléphone masqué le reste même après acceptation de la demande ; le chat interne reste utilisable. Ne pas appliquer encore `autoriser_messagerie` : son interface et ses règles restent à préciser, les flux existants sont conservés.
- Mesures : `TASKLY_PERF_TIMING=true` (uniquement en préproduction) ajoute `Server-Timing` pour les lectures utilisateur/artisan de l'authentification, durées en ms, aucune donnée personnelle. Cela inclut l'attente de la requête SQL/pool et réseau vers TiDB, pas seulement l'exécution SQL. Ce n'est pas la durée totale de la requête ni le TTFB. Désactiver en production.

## Tests réellement exécutés

- `npm run check` : 181 fichiers JS, aucune erreur.
- `node --test tests/audit-v2.test.js` : 8 tests réussis sur 8 (mocks SQL/Redis et navigateur simulé via VM, contrôles du code et appels de fonctions). Pas de Redis ni TiDB réel.
- `npm test` : 250 réussites, 11 échecs de chargement ou d'exécution liés aux dépendances express/bcrypt/multer/nodemailer absentes (voir synthèse). V1 : 242 réussites, 11 échecs ; original : 231 réussites, 15 échecs. Les 11 échecs restants ne permettent pas de conclure que les tests d'intégration passent. L'installation hors ligne des dépendances avait échoué lors de V1 ; lockfile inchangé.
- Essai Chromium/Playwright avec pages générées à partir des vraies sources et API fictives, navigation interdite par l'environnement (`ERR_BLOCKED_BY_ADMINISTRATOR` sur domaine de test et localhost). Aucune validation visuelle revendiquée. Les deux simulations DOM V1 des modales restent réussies.
