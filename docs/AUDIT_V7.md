# Taskly V7 — Relance Taskly Mail et diagnostic des performances

Version cumulative de la V6, sans modification de production. L'objectif de cette passe est de corriger un blocage du parcours de demande et d'améliorer l'observabilité avant les mesures réelles. Les fonctionnalités précédentes sont conservées dans l'archive.

## Changements

- `server/services/professionalMailPolicy.js`, `server/routes/professionalMailRoutes.js`, `client/public/js/professional-mail-pilot.js` : une demande annulée peut être redéposée depuis le même espace, avec le même profil, métier et e-mail personnel, après 60 secondes minimum depuis le dernier envoi du code. L'adresse reste réservée au profil, le code est renouvelé, les tentatives et la date de confirmation réinitialisées. Une demande refusée, en attente de décision ou approuvée ne peut pas revenir au stade de confirmation. Un changement de profil requiert toujours le support. La version du script est actualisée sur les deux pages.
- Les empreintes de confirmation exigent maintenant un secret d'au moins 32 octets et normalisent l'identifiant numérique SQL. Les empreintes précédentes calculées avec un identifiant numérique sont compatibles ; un code ancien calculé avec un identifiant chaîne peut nécessiter un renvoi.
- `server/services/professionalMailGateway.js` : validation plus stricte des destinataires (adresse ASCII simple, partie locale de 64 caractères maximum et labels DNS valides) ; rejet des listes de messages avec identifiants dupliqués, des curseurs malformés ou répétés immédiatement. Une réponse invalide du fournisseur est traitée comme indisponibilité 503, pas comme faute de saisie utilisateur. Ce sous-ensemble n'accepte pas tous les formats d'adresse RFC (adresses internationalisées, locales entre guillemets). Le fournisseur réel doit assurer l'isolation effective des boîtes et la déduplication des envois.
- `server/helpers/performanceTiming.js`, `server/app.js`, `server/services/sessionActivity.js` : diagnostic opt-in avec `TASKLY_PERF_TIMING=true`. L'en-tête `Server-Timing` expose `session_middleware` (temps du middleware de session, qui inclut éventuellement la lecture Redis) et `session_save` (temps de sauvegarde explicite via `/api/auth/activity`), en complément de `auth_user_sql` et `auth_artisan_sql` de V2. Les durées ne contiennent ni secret, ni identifiant. Ce ne sont pas des mesures de latence Redis pure. Les contrôles d'accès et la durée d'inactivité de 4 h ne sont pas modifiés. Garder ce flag désactivé hors diagnostic de préproduction.
- Aucune nouvelle migration SQL V7.

## Tests réellement exécutés

- `npm ping --fetch-retries=0 --fetch-timeout=5000` : EAI_AGAIN, résolution DNS du registre npm indisponible. Les dépendances ne peuvent donc toujours pas être téléchargées ici.
- `node --test tests/audit-v7.test.js` : 7/7 réussis (règles et route de redemande, secret, format d'adresse, pagination de la passerelle, mesures optionnelles et préservation des erreurs du middleware).
- `npm run check` : 191 fichiers JavaScript contrôlés, aucune erreur de syntaxe.
- `npm test` : 291 réussites sur 302 résultats ; 11 échecs `MODULE_NOT_FOUND` (Express, bcrypt, Nodemailer, Multer), identiques à V6. Le test des routes mail utilise des mocks ; aucune boîte réelle créée ni aucun e-mail envoyé.
- Pas de navigateur connecté, pas de mesure de charge, pas de test réel de base, Redis, SMTP ou fournisseur mail. Les correctifs ne constituent pas une certification de sécurité.

## Suite prioritaire : valider la préproduction, pas multiplier les ZIP sans mesure

1. Créer une branche de travail à partir du dépôt actuel, comparer celui-ci au ZIP initial et réconcilier les modifications faites entre-temps. Ajouter les fichiers V7 (y compris `.github` et migrations) sans committer les secrets. Ne pas remplacer la branche principale.
2. Node 22 et `npm ci`, puis `npm run check`, `npm test`, `npm audit --omit=dev --audit-level=high` sur environnement connecté. Corriger les éventuels échecs réels ; le CI doit passer.
3. Configurer une base TiDB de test et un Redis distinct, un secret de session distinct, une URL Preview et des e-mails de test ; `npm run preview:check` et vérification manuelle de l'isolation. Ne pas diriger le cron/worker vers la production. Migrer la copie de test seulement après sauvegarde. Voir les rapports V1–V6 pour l'ordre des migrations.
4. Vérifier les quatre espaces, le cycle de connexion et déconnexion, changement d'espace, les fenêtres modales, les justificatifs, la confidentialité et les notifications. Ne pas masquer les anomalies.
5. Pour la lenteur de `/api/auth/me` et `/api/auth/activity` : activer temporairement `TASKLY_PERF_TIMING=true` uniquement dans Preview, relever `Server-Timing` et TTFB dans DevTools, au moins 10 navigations comparables, distinguer démarrage à froid et chaud. Comparer régions Vercel/TiDB/Redis et résultats ; ne pas changer les régions sans vérification. Désactiver le flag une fois le diagnostic terminé. Aucun gain chiffré réel n'est revendiqué.
6. Taskly Mail : laisser les deux flags à `false` tant que le fournisseur réel et son cycle de vie ne sont pas validés. Le domaine/DNS, provisionnement, activation indépendante, mot de passe et récupération, pièces jointes, corbeille, recherche, antispam et stockage réel restent incomplets. En particulier, définir et tester la révocation/suppression des boîtes et la réservation des adresses après suppression d'un compte : les cascades SQL ne suppriment pas automatiquement une boîte externe et le provisionnement externe doit être réconcilié en cas d'échec. Ne jamais attribuer à une autre personne une ancienne boîte ou ses données. Ce point bloque l'activation du fournisseur en production.
7. Faire les tests de charge progressifs sur un environnement autorisé et isolé. Un million de comptes enregistrés n'est pas une capacité démontrée ; distinguer stockage et concurrence. Obtenir la validation du propriétaire et prévoir le retour arrière avant toute fusion/déploiement de production.
